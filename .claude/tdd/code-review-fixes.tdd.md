## User journeys covered
- As the app's owner, I want the quick-add modal on `/settings` to work the same as on every other page, so I can log a transaction from anywhere without it silently failing.
- As the app's owner, I want clicking an uncategorized ("NO CATEGORY") chart slice to actually show me those transactions, so drill-down is trustworthy everywhere, not just for named categories.
- As the app's owner, I want the Top Merchants/Recurring links to filter the table that actually has that data.
- As the app's owner, I want renaming/merging a category with a budget or kind change to never silently lose that change.
- As the app's owner, I want category name/budget input to be validated so a bad request 400s instead of 500ing.
- As the app's owner, I want the app to survive concurrent first requests after a deploy without a stray 500 or duplicated seed data.
- As the app's owner, I want the ingestion log to tell me how many transactions were skipped because they were internal transfers vs. real duplicates.

## Coverage and known gaps
- **Full backend suite**: `pytest tests/ -v` → **297 passed** (up from 276 at the start of this session's baseline commit `e63dd6a`; no `pytest-cov` configured in this repo, so no numeric coverage percentage — every new/changed function has at least one direct test, per the table above).
- **No JS test runner exists in this repo** (`frontend/` has zero build step, no Jest/Vitest/Bun test config) — this was true before this session and is unchanged by it. The 6 frontend findings (HIGH-1, HIGH-2, MED-3, LOW-MED-8, LOW-9, LOW-10) therefore could not go through automated RED/GREEN. They were instead: (a) implemented per the design plan's exact code-level direction, (b) syntax-checked with `node --check` on every touched file, (c) CSS brace-balance-checked, and (d) for the 4 with an observable effect, verified live against a running server via Chrome DevTools MCP (see rows 12–15 above) — including two regression checks (a real category still filters correctly; the modal's loading-spinner button is unaffected by the CSS consolidation). LOW-MED-8's fix (the toast branch) could not be independently exercised this way, because the current quick-add form has no account-number field, so no manually-created transaction can actually match an ignore rule to produce the 200 response — this is a pre-existing form limitation, not a gap introduced by this fix, and is called out explicitly as out of scope in the plan.
- **Known gap, disclosed in the plan and intentionally not tested**: the optional flaky-risk raw multi-threaded `init_db()` stress test (mentioned in the design pass) was not added — the deterministic tests (`test_add_column_tolerates_losing_race`, `test_init_db_dedupes_existing_ignored_transfer_duplicates`, `test_create_duplicate_rule_is_idempotent`, `TestLazyDbInit`) are the actual proof for MED-6, per the plan's own guidance.
- **One incident during implementation**: an `sd` (sed-like) regex replacement in `frontend/js/app.js` (LOW-10) initially stripped the `${year}`/`${month}` template-literal interpolations from all 5 call sites. This was caught immediately by `node --check` + a manual diff read, and fixed with 5 targeted edits before committing — the committed code (verified above) is correct.
